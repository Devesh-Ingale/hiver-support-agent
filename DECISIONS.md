# Decision log

Plain list of the non-obvious decisions, in the order they were made. Each entry says what was decided and why; where a decision was later revisited, the entry is amended rather than deleted.

## Pre-registered acceptance gate (written 2026-09-09, before any model output existed)

The agent is "good enough to trust" for auto-handling only if, on the frozen 200-item test set:

1. Recall on **hard** escalation categories (account/PII, payment/refund, legal/safety/threat, explicit human request) ≥ 0.95, with the bootstrap 95 % lower bound ≥ 0.85.
2. Zero hard validity violations on drafts the agent chose to auto-send (over 280 characters, URL not present in retrieved evidence, request for sensitive data in public, promise of refund/timeline/fix, fake agent sign-off, anonymised-handle artefacts).
3. Judge pass-rate ("a brand agent would send this with at most a light edit") ≥ 70 % on auto-handled drafts.
4. Expected cost per 100 messages (missed hard escalation = 10, missed soft = 3, unnecessary escalation = 1) below the always-escalate baseline.
5. Automation rate is reported at the operating point where missed hard escalations ≤ 2 %.

The report ends with a verdict against exactly these five conditions. They will not be edited after test-set results are seen.

## Decisions

1. **Headline system runs on a local open model (Ollama, ~4B parameters), not a hosted frontier model.** Iteration is unlimited and reproducible without any API key, which matters more here than raw quality: the assignment grades the proof, not the system. A single run of the same prompts on `gemini-3.8-flash` is reported as a "stronger model" row so the reader can see what the ceiling looks like.
2. **The LLM judge is a different model family (`gemini-3.8-flash`) from the generator.** Same-family judging is known to favour its own style (self-preference). Splitting families removes that bias by construction; the remaining judge risk is measured directly by the human-agreement study.
3. **Unit of prediction = the first inbound customer tweet of a thread.** Multi-turn handling is out of scope (see report §"what I chose not to build"). This keeps labels unambiguous and matches how a triage system first sees a message.
4. **"Historical resolution" = all brand-side turns of the thread, not the first reply.** In this dataset the first brand reply is very often a clarifying question or a "DM us" redirect; the substance, when it exists, arrives later. Each brand turn is tagged by type (steps / link / DM-redirect / question / apology-only) so boilerplate can be down-weighted in retrieval and quantified in the report.
5. **Retrieval is TF-IDF (word + character n-grams), not sentence embeddings.** Tweets are short and vocabulary-driven; TF-IDF is transparent, fast, and keeps the reproduction path free of a torch download. Embeddings are on the "next week" list if retrieval quality on the dev set turns out to be the bottleneck.
6. **One structured LLM call per message, followed by a deterministic post-processor.** The model returns intent, reply, decision, reason and evidence ids in a single JSON-schema-constrained response; hard escalation rules and tweet-validity checks are plain Python. That keeps the API budget at one call per item and makes the safety-critical logic testable and easy to modify live.
7. **The model's self-reported confidence gates nothing.** LLM confidences are poorly calibrated; "no relevant historical resolution" is a deterministic retrieval-similarity threshold tuned on the dev set. Self-reported confidence is only reported as a reliability table.
8. **Labelled data is split into 200 test + 50 dev, and the test set is frozen (committed) before any prediction exists on it.** All prompt and threshold iteration touches only dev; the touch log above records every test-set computation.
9. **Golden set sampling is two-part: 120 uniform-random (Part A) + 80 targeted (Part B).** Part A gives honest natural-distribution estimates; Part B (cluster floors + escalation-keyword oversample) gives per-intent support and enough escalation positives. Every table states which part it uses.
10. **Reply quality is scored with binary checks + pass/fail + a pairwise comparison against the verbatim-retrieval baseline, not a 1–5 multi-dimension rubric.** Binary and pairwise judgments are more reliable for both LLM and human raters; 1–5 scales compress to 4s and 5s.
11. **Escalation ground truth is a written policy applied blind by the labeller, and the same text is given to the model.** The metric therefore measures "does the system apply the policy the way a person would", which is legitimate as long as the policy is frozen before labelling and never edited after seeing test errors.
12. **Banking77 is not used.** Its 77 banking intents do not transfer to a consumer-tech/entertainment brand's Twitter traffic; a taxonomy induced from the brand's own data is more faithful.

13. **Local model = `qwen3:4b-instruct`, chosen by an 8-tweet smoke test against `qwen3.5:2b` and `llama3.2:3b` (2026-09-09, no retrieval, example taxonomy).** All three returned schema-valid JSON 8/8. Only Qwen3-4B made sound escalation calls: it auto-handled a feature request and praise, escalated billing/hacked-account/"speak to a real person" with the right codes. Qwen3.5-2B escalated the feature request as `explicit_human_request` and labelled an emoji-only tweet `account_access`; Llama-3.2-3B escalated neutral bug reports as `anger_churn` and the feature request too. Qwen3-4B is ~2.3× slower (≈10.5 s vs ≈4.5 s per call on the GTX 1650), i.e. ~45 minutes per 250-item run — acceptable for unlimited offline iteration. The judgment gap mattered more than the speed gap.
14. **Retrieval boilerplate penalty = 0.2 (multiplicative on cosine for threads where the brand never gave steps or a link).** Boilerplate "DM us" threads only win a slot when nothing substantive is close; the raw similarity is still reported untouched and is what the "no relevant resolution" floor uses.

15. **Brand = SpotifyCares, chosen from a profile of the 15 largest brands (2026-09-09; `outputs/results/brand_profile.csv`).** Criteria: enough history for retrieval, a real mix of public help and private hand-offs (so the auto-vs-escalate boundary is learned from the brand, not only from our policy), and a product narrow enough for ≤10 intents. SpotifyCares: 28.2k customer threads (20.9k before the cutoff, 6.4k in the 14-day golden window); 40 % of threads get substantive help; brand turns are 8.5 % steps / 25 % links / 31 % DM-redirects / 18 % clarifying questions; 92 % English. Runners-up: AppleSupport (80k threads, 18 % step-giving turns, but 53 % identical "let's take this to DM" boilerplate) and hulu_support (67 % substantive but only 14.8k threads and it almost never hands off to DM, so escalation labels would rest on policy alone). This choice biases the reply-quality result upward relative to boilerplate-heavy brands — stated in the report's "misleading" section.
16. **Anonymised handles: the brand's own main account is treated as the brand.** The dump rewrites every non-support handle as `@<number>`; for SpotifyCares 45 % of customer tweets address `@115888`, which is @Spotify, not another customer. Ids mentioned in ≥ 10 % of a brand's roots are detected as aliases, mapped to `<brand>` in cleaning, and excluded from the "mentions another customer" flag (which is then ~16 %). Without this, half the golden set would have been mis-flagged as replies to other customers.

17. **Taxonomy v0: ten intents including `other_unclear`, written by hand from 20 TF-IDF clusters over 3,000 pre-cutoff tweets (2026-09-09, before any label or prediction).** A local-model proposal (`outputs/results/taxonomy_proposal.md`) was consulted as a cross-check; it agreed on the core (account security, subscription, family plan, app malfunction) but split catalogue requests into song/album/feature and gave Discover Weekly its own class — too granular for ~200 labels, so those were merged into `content_request_or_availability`, `feature_request_or_feedback` and `library_or_playlist_problem`. Two classes the proposal lacked were added because the brand handles them differently: `account_settings_change` (country/username/deletion — help-article territory) and `support_followup_or_complaint` ("reply to my DM" — a human must act). Escalation reasons are tiered hard / soft / routing; the hard tiers carry regex patterns that fire on 16 % of golden candidates (10 % payment, 5 % account access). Frozen as v1 after a 30-item labelling pilot; only merges and clarifications are allowed at that point.

18. **Judge model = `gemini-3.5-flash-lite`, not `gemini-3.8-flash` (2026-09-10).** The free tier allows exactly **20 requests per day** of `gemini-3.8-flash` (`generate_content_free_tier_requests, limit: 20` in the 429 body); a ~1,500-call judging plan is impossible on it, and the SDK's silent retries had turned that quota wall into 70-second "latencies". `gemini-3.5-flash-lite` answers the full judge prompt in ~1.2 s without a thinking phase, gave the right verdict on the fabricated-step probe, and remains a different model family from the Qwen generator. The cost of the change is a weaker judge — which is exactly what the human-agreement study measures, so the report states it rather than assuming it away. The client now treats three consecutive 429s as the daily quota (stop cleanly, resume tomorrow) instead of backing off for minutes.

19. **Taxonomy frozen as v1 after a 41-item pilot (2026-09-11), with clarifications only.** The pilot labels applied the ten intents consistently (content requests 29 %, payment 22 %, account access 17 %; 20/41 escalated, half of those for account/PII). Three items looked like keying slips and were sent back for re-entry by the labeller; nothing was relabelled by anyone else. Two definitions were sharpened without changing class boundaries: a HiFi *tier* is a product feature request (not catalogue availability), and being charged twice (Premium plus the student price) is a billing error with plan eligibility as the secondary intent. No intent was merged or split. The pilot also showed the labeller used confidence 3 and anger 0 throughout — the label-noise-by-confidence table will therefore be thin, and the report says so.

20. **Judge budget fitted to the measured free tier (AI Studio dashboard, 2026-09-11): `gemini-3.5-flash-lite` 15 RPM / 500 requests per day; every other current Flash (3.5, 3.6, 3.7, 3.8) 5 RPM / 20 per day.** Plan: day 1 — absolute judging of `main` (200), `simple` (200) and the brand's real replies (100); day 2 — pairwise `main` vs `simple` in both orders (≈150 items → 300 calls), `trivial` and `no_rag` on 50 items each, and a 50-item paraphrased-prompt consistency probe. Runs are cached and resume across days; the client stops at the quota instead of retrying. The "same prompts on a hosted model" comparison row cannot run 200 agent calls on a 20-per-day model. **Resolved 2026-09-12:** `gemini-3.1-flash-lite` (not shown on the dashboard) completed 50 dev items without a quota error at 1.7 s/call, so the row runs on it (`gemini_agent_model`), kept distinct from the judge model so the judge never scores its own drafts. On dev it agreed with the local model on 37/50 intents and 43/50 decisions.

21. **The remaining 209 golden labels were produced by the AI assistant, not by the author, and the report says so (2026-09-12).** The 41 pilot items were labelled blind by the author. For the rest, two models proposed a label per tweet — `gemini-3.5-flash-lite` and the local `qwen3.5:2b`, deliberately *neither* the system under test — and the AI coding assistant (Claude) that built the pipeline accepted the proposal where the two agreed and adjudicated every disagreement by reading the tweet against the frozen taxonomy and checklist, also overriding agreed proposals it judged wrong. No item-level review by the author took place. Every row is stamped `labeller: assistant` with its `label_source` (`proposals_agreed` or `assistant_adjudicated`) and both proposals. Why: the author decided their time could not go to labelling; the alternative was no evaluation at all. Cost, stated plainly in the report: the labels encode an AI's reading of the taxonomy, so the evaluation measures agreement between systems and an AI-authored key, not with a human — the strongest possible objection to the headline numbers. Mitigations reported: proposer accuracy on the blind human labels; results split by proposer agreement; the author's blind round-2 re-label of 40 items, which now measures human agreement *with the AI-made key*. **Outcome (2026-09-12):** 250 labels = 38 blind author + 212 assistant (157 adjudicated where the proposers disagreed, 55 agreed proposals accepted; the author's three pilot slips were re-decided by the assistant). Against the 38 blind labels the proposers scored: Gemini 3.5 Flash-Lite 84 % intent / 87 % escalate / 79 % reason code; Qwen3.5-2B 61 % / 84 % / 66 %; the two agreed on intent for 63 % of items and were right 87.5 % of the time when they did. Final key: 48 % escalate (account/PII 45, payment 48, explicit human 10, anger 6, no content 6, non-English 5, legal 1); intents led by payment (54), playback (38), account access (36), feature/feedback (35), content (29).
